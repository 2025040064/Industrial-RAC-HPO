# S3.0 报告：S2 等轮数消融的统计补全与口径核验

> 日期：2026-11-25
> 阶段：S3.0（补全 S2 实验的统计推断与口径核验）
> 性质：对 S2 正式消融（120 轮 = 4 组 × 3 种子 × 10 轮）的补全，**不重跑实验、不修改冻结基线**

---

## 1. 定位与边界（先声明，避免误读）

本报告是对 S2 已产出的 120 轮原始结果（`experiments/s2-ablation-b-20261125/results/ablation-results.json`）的**统计补全与口径核验**，不是新实验。

**三条不可逾越的边界**（贯穿全文）：

1. **等轮数 ≠ 等 CPU 预算**。S2 是等轮数（每组每种子 10 轮连续优化）实验，**不是**严格等 CPU 预算实验。等 CPU 预算的对照留待 S3.6。
2. **公开验证 ≠ 跨设备泛化 ≠ 隐藏集**。本报告所有统计结论的口径是**公开验证集 RMSE**（本地唯一可测口径）。
3. **RMSE 数值一致 ≠ Checkpoint 逐字节一致**。指标一致性与模型文件 SHA 一致性是两回事，必须分开核验。
4. **父链 SHA 连续 ≠ 不同父模型指标可混合**。父链连续只保证"每轮父模型 = 上一轮选中模型"这一**因果链完整**，**不保证**不同父模型（不同起点 RMSE）下的绝对候选指标可直接混合进代理拟合（详见 §5.5）。

---

## 1.5 严格等 CPU 预算消融的状态（S3.0 遗留 → 归入 S3.6）

用户要求 S3.0 补做"严格等 CPU 预算消融"。经核验（§5.3），**本地与平台 CPU 计量口径不可通约**（平台 `cpu_seconds` 组成不可从 report 获知），因此：

- **严格等 CPU 预算实验无法在 S3.0 内以"平台 695.89s"为锚完成**——任何折算都是无依据的猜测。
- 正确做法是**在 S3.6 重新预注册一套纯本地的 CPU 预算协议**（所有组共享同一 `process_time()` 口径的预算上限），届时完成"固定超参 / 随机搜索 / 标准 TPE / 原始 RAC / 改进 RAC"的严格等预算对照。
- **本报告不宣称已补做等预算消融**，只补做统计推断与口径核验。等预算消融作为 S3.6 的正式交付项，其预注册协议将在 S3.6 阶段先行冻结。

## 3. 配对种子差值（同一 seed 下组间差）

这是本报告的**核心推断口径**：3 个种子是**配对**的（同一 seed 驱动 4 组），因此组间差必须在种子层面配对后再求均值，而不是对两组均值直接相减。

| 效应 | seed 42 | seed 2024 | seed 7 | 配对均值 | 样本 sd | se | t (df=2) |
|---|---|---|---|---|---|---|---|
| EMA@lr1e-5 (G1−G0) | +8.59 | +4.12 | −2.41 | +3.43 | 5.54 | 3.20 | 1.07 |
| EMA@lr3e-3 (G3−G2) | +20.23 | +25.10 | +21.95 | **+22.43** | 2.47 | 1.42 | 15.75 |
| lr@EMAoff (G2−G0) | −12.39 | −31.78 | −31.36 | **−25.18** | 11.08 | 6.40 | −3.94 |
| lr@EMAon (G3−G1) | −0.75 | −10.80 | −7.00 | −6.18 | 5.08 | 2.93 | −2.11 |

### 3.1 析因主效应与交互（配对种子口径）

| 效应 | per-seed 值 | 配对均值 | 样本 sd |
|---|---|---|---|
| lr 下限主效应 = mean(G2−G0, G3−G1) | −6.57 / −21.29 / −19.18 | **−15.68** | 7.96 |
| EMA 主效应 = mean(G1−G0, G3−G2) | +14.41 / +14.61 / +9.77 | **+12.93** | 2.74 |
| 交互 = (G3−G2) − (G1−G0) | +11.64 / +20.98 / +24.37 | **+19.00** | 6.59 |

### 3.2 效应量（配对 Cohen's d，明确公式）

**公式说明（本报告采用 Lakens (2013) 推荐的配对效应量 d_av）**：

```
d_av = mean(配对差值) / pooled_sd(两组)
pooled_sd = sqrt((sd_A² + sd_B²) / 2)
```

> **为什么不用 d_z**：d_z = mean(差值) / sd(差值序列) 的分母是"配对差值序列的标准差"，当种子间差值高度一致时（sd(差值) 很小），d_z 会被**严重放大**（如 EMA@lr3e-3 的 d_z=9.09 虚高）。d_av 用两组的 pooled 标准差作分母，与独立样本 Cohen's d 可比，适合跨配置/跨研究比较。**本文全部采用 d_av**。

| 对比 | d_av (配对) | d_z (仅供对照) | 解释（Cohen 惯例） |
|---|---|---|---|
| EMA@lr1e-5 (G1 vs G0) | +0.56 | +0.62 | 中效应 |
| EMA@lr3e-3 (G3 vs G2) | +2.59 | +9.09 | 大效应（有害） |
| lr@EMAoff (G2 vs G0) | −2.82 | −2.27 | 大效应（改善） |
| lr@EMAon (G3 vs G1) | −1.07 | −1.22 | 大效应（改善） |

> **修正说明**：S3.0 报告初版 §3.2 的"d（配对）"实际是 **d_z**（分母为差值序列 sd），未标明公式。本版已改为 **d_av** 并明确公式。d_z 仅供对照，不作为结论依据。

**修正声明**：S3.0 报告初版 §4 只列出了 4 个"简单效应"的置信区间，漏列了 2 个"主效应 + 交互"的置信区间，却据此得出"唯一不跨零的是 EMA@lr3e-3"——这是**逻辑错误**。完整计算后，n=3 下**不跨零（显著）的效应有 3 个**：

1. **EMA 主效应 +12.93，95%CI [6.13, 19.73]**——不跨零，EMA 在公开验证口径下显著有害。
2. **交互效应 +19.00，95%CI [2.62, 35.37]**——不跨零，EMA 与 lr 下限存在显著正交互（两者联合放大了害处）。

## 5. 口径核验（对应 S3.0 要求 5/6/7/8）

### 5.1 等轮数 ≠ 等 CPU 预算（要求 5）

S2 是**等轮数**实验（每组每种子 10 轮连续优化），各组训练内核（EMA on/off）的 CPU 成本**并不相同**：

| 组 | 训练内核 | 总 CPU(3 种子) |
|---|---|---|
| G0 | 直接 epoch-end | 5.8s |
| G1 | EMA（epoch 内 blend） | 1.9s |
| G2 | 直接 epoch-end | 1.9s |
| G3 | EMA | 2.0s |

- G0 的总 CPU 显著高于其他组，说明**各组并未消耗相同 CPU 预算**。
- **因此 S2 的任何"单位 CPU 收益"（RMSE↓/s）都不能作为跨组公平比较依据**，只能作为组内相对参考。S2 报告 §8 已就此加注，本报告再次强调：**不得将等轮数实验描述为等 CPU 预算实验**。
- 严格等 CPU 预算的对照（固定超参 / 随机搜索 / 标准 TPE / 原始 RAC / 改进 RAC）留待 **S3.6**，届时所有组共享同一预注册 CPU 预算。

### 5.2 平台 validation_metrics 与 old/new 的真实语义（要求 6）

**核验结论（修正 S2_PREAUDIT.md 的一处错误）**：

| 符号 | 代码来源 | 真实语义 |
|---|---|---|
| `old` | `contest_submission.py:230` `platform_metric(rnd.frame.get("current_validation"), metric)` | **平台在每轮开始注入的「当前父模型公开验证集指标」** |
| `new` | `contest_submission.py:330` `platform_metric(submission.get("summary"), metric)` | **平台对刚提交候选的「公开验证集指标」**（`submit_candidate` 的 `candidate_response` 返回） |
| `validation_metrics` | 平台 report `rounds[].validation_metrics` | **每轮公开验证集指标**（B 任务 round1 rmse=665.71，与本地复现完全一致） |
| 隐藏集指标 | 平台 report `report.metrics` | **最终评测一次**（B 任务 rmse=486.08），**只在最终 report 出现，不参与每轮 old/new** |

**关键修正**：S2_PREAUDIT.md 第 94 行曾写"平台主指标 old/new 来自隐藏集"，**这是错误表述**。经源码核验（`contest_submission.py:230/330` + SDK `round.py:submit_candidate` + 平台 report 逐轮字段）：

- **old/new 是公开验证集指标**（`validation_metrics`），**不是隐藏集**。
- 隐藏集指标只在最终 `report.metrics` 评测一次，**从不**作为每轮 old/new 参与接纳决策。
- 因此，v6 平台的逐轮接纳决策（`improved`）**完全由公开验证集驱动**，与本地 S2 消融的口径**一致**（都用公开验证 RMSE 判 improved）。

> 这一修正**不影响 S2 的结论**（S2 本就用公开验证口径），但**纠正了"平台用隐藏集驱动逐轮决策"的误解**，也澄清了 S3.1.5"本地 vs 平台搜索轨迹差异"的真实来源：**不是公开验证 vs 隐藏集驱动之差，而是（a）PyTRIO 决策服务通道（平台 RPC vs 本地直连 sampler）与（b）决策 prompt 的历史内容（平台含 platform_parent_metric=old，本地用 local_parent）之差**。

### 5.3 本地与平台 CPU 计量口径（要求 7）

**核验结论：不得将本地/平台 CPU 时间差异直接归因于"虚拟 CPU 配额"。**

| 项 | 本地 S2 | 平台 v6 B 任务 |
|---|---|---|
| 单轮训练 CPU | ~0.01s | 无逐轮拆解（report 仅聚合值） |
| 10 轮总 CPU | 1.9~5.8s | 695.89s（`cpu_accounting_status="measured"`） |
| 计量内容 | 仅 `time.process_time()`（本地续训+验证） | **平台侧聚合值，组成不可从 report 获知** |

- 相差 ~120~350 倍（695.89 / 1.9~5.8），**不是**此前 S2 报告 §8 写的 ~7000 倍（那是以"单轮 0.01s"为基准的口径混算；以 10 轮总 CPU 计，实际约 120~350 倍）。
- **真实证据边界（本次已修正）**：平台 report 的 `rounds[]` **不含任何 CPU 分项字段**（已核验：首轮 keys 无 cpu/cost/second 相关字段），只有聚合的 `cpu_seconds=695.89` 和 `wall_seconds=846.12`。容器内代码自计的 `cpu_breakdown_seconds`（preload/search/training/validation/sdk_rpc）写进 `selection-audit.jsonl`，**已随容器销毁，本地不可得**。
- **因此**：初版 §5.3 声称"差异来自 SDK RPC/隐藏集评测/模型推理"是**未经证实的推断**，已撤回。真实可确认的只有两点：(a) 本地与平台 CPU 计量**确实不同**（差 ~120~350 倍）；(b) 平台 `cpu_seconds` 的**具体组成不可从 report 获知**。**"虚拟 CPU 配额"没有任何证据支持，但"SDK RPC/隐藏集评测"同样没有 report 级证据支持**，二者都只能标为"未证实"。
- **结论**：S3.6 做严格等预算实验时，必须**重新预注册一套本地 CPU 预算协议**，以本地统一的 `process_time()` 口径为锚，**不得**用平台 695.89s 直接折算成本地预算，也**不得**声称已定位平台 CPU 的具体去向。

### 5.4 RMSE 数值一致 ≠ Checkpoint 逐字节一致（要求 8）

S2_PREAUDIT 的固定回放结论是"round1-3 RMSE diff=0.0000"，这证明的是**指标一致性**，**不是**模型文件逐字节一致：

| 核验对象 | 已核验 | 结论 |
|---|---|---|
| RMSE 数值一致 | round1-3 diff=0.0000，round4+ 浮点累积 +0.0166 | **指标一致**（前 3 轮精确） |
| Checkpoint SHA 逐字节一致 | 本地 `model_sha()`（权重+Adam state 排序后 hash） | **仅本地父/候选/选中链内自洽** |
| 平台 artifact SHA | 平台 report 只暴露 `artifact_id`，不含逐字节 SHA | **不可本地复现**（容器已销毁） |

- 本地回放的"RMSE 一致"只说明**续训机制（父检查点 + lr/bs/ep + EMA）忠实复现了平台公开验证指标**，**不能**据此断言"本地模型文件与平台 artifact 逐字节相同"。
- 平台的 `parent_sha256`/`candidate_sha256`/`selected_sha256` 的逐字节一致性，只能由平台 `selection-audit.jsonl`（已随容器销毁）证明，本地无法重建。
- **S3 后续任何"复现"表述，必须区分「指标一致性」（可本地证明）与「Checkpoint SHA 一致性」（仅平台可证明）两个层级。**

### 5.5 父模型历史可比性（S3.0 新增，承接 S3.1.3）

**核验结论：父链 SHA 连续 ≠ 不同父模型的绝对指标可直接混合。**

以 G2 seed2024 为例（`run-G2-seed2024-r10.json`），10 轮中父模型发生了 **2 次 promote**，跨越 **3 个不同父模型**：

| 父模型 | 父 RMSE（起点） | 覆盖轮次 |
|---|---|---|
| 父A（sha 5b4b2859） | 681.16（基线） | round1 |
| 父B（sha fcc341e1） | 657.65 | round2-5 |
| 父C（sha fb44c192） | 617.46 | round6-10 |

- 父链 SHA 连续（每轮 parent = 上轮 selected）保证了**因果链完整**，但历史 records 里每条 `robust_objective`（代理拟合的 target）是**该候选相对其自身父模型的绝对 J 值**。
- 父B 起点 657.65 下的候选 J，与父C 起点 617.46 下的候选 J，**绝对值不可直接比较**——因为起点不同，"候选 J=0.9"在父B 是改善、在父C 可能是恶化。
- **这正是 S3.2 要求 4 的核心动机**：改用**相对父模型收益 R = (E_parent − E_candidate)/(E_parent + ε)** 作为代理预测目标，而非绝对 RMSE。原始 `_trial` 的 objective 是绝对 J，跨父混合存在可比性隐患。

> 补充发现：G2 seed2024 的 round2-4 出现 `objective_improved=True` 但 `accepted=False`（主指标 RMSE 未改善），说明**鲁棒目标 J 与主指标 RMSE 可能方向不一致**（J 改善但 RMSE 恶化）。这是 S3.3 鲁棒目标研究的一个独立线索，此处仅记录。

## 6. S3.0 结论汇总

1. **统计显著性**：n=3 下不跨零（显著）的效应有 3 个——EMA 主效应 +12.93（CI[6.13,19.73]）、交互效应 +19.00（CI[2.62,35.37]）、EMA@lr3e-3 +22.43（CI[16.30,28.56]）。lr 主效应 −15.68 方向一致但 CI 跨零，**不能宣称已证实**。
2. **口径**：S2 是等轮数实验，不是等 CPU 预算实验；等预算对照留 S3.6。
3. **平台语义修正**：old/new 是公开验证集指标，不是隐藏集；隐藏集只在最终 report.metrics 评测一次。
4. **CPU 口径**：本地/平台 CPU 差异真实存在（~120~350 倍），但平台 `cpu_seconds` 的组成**不可从 report 获知**，既无证据支持"虚拟 CPU 配额"，也无 report 级证据支持"SDK RPC/隐藏集评测"等具体去向——均标"未证实"。
5. **一致性分层**：RMSE 数值一致（指标层，可本地证明）≠ Checkpoint SHA 一致（字节层，仅平台可证明）。
6. **G2 的处置**（对应 S3.0 要求 2）：G2（EMA off + lr 3e-3）作为**训练侧待验证候选**，**不直接替代 v6**。其"公开验证最优"（628.40）与"小样本轴承泛化最差"（Bearing1_4 +109）的矛盾，正是 S3.3 鲁棒目标优化的动因。
